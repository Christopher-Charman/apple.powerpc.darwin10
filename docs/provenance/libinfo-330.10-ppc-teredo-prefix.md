# Libinfo-330.10: 32-bit Teredo prefix conversion

Apple's official 10.6.8 release manifest (`source-releases/10.6.8.json`) selects `Libinfo-330.10`, tag commit `614293f557dbfe060fa137bc133de8b79790e4c5` at [Apple OSS](https://github.com/apple-oss-distributions/Libinfo/tree/Libinfo-330.10). The tracked working component and immutable `src/releases/10.6.8/Libinfo-330.10/` snapshot were byte-identical before this change (component tree `9859501abf0a68331a2f4c53fdbd00aa4109dc2d`; `lookup.subproj/si_getaddrinfo.c` blob `780a13368aca539601acc6e6f2a9bc528cfe0b89`). Apple's 10.5.8 release lists `Libinfo-278.0.3`; the PPC-compatible Snow Leopard predecessor `Libinfo-324.1` (tag commit `696adf4cfed7ac64ae7032bafee0312ea9adfe48`) has no `_si_net_addr_type` classification. The Teredo check was added between those revisions, so there is no predecessor implementation to restore.

In `_si_net_addr_type`, the first 32-bit word of an IPv6 address is compared with `ntohs(TEREDO_PREFIX_32)`, where `TEREDO_PREFIX_32` is `0x20010000`. `ntohs` is a 16-bit conversion: the constant truncates to zero. On big-endian PowerPC, a real `2001:0000::/32` prefix reads as `0x20010000`, so the check misses it; a zero first word can be misclassified. The same width error affects little-endian hosts. Changing the conversion to `ntohl` matches the 32-bit address field on both endian orders. The adjacent 16-bit 6to4 check remains untouched. This changes IPv6 address classification used by network configuration statistics and destination sorting; it does not alter DNS packets or ABI.

Exact working-source diff: `patches/Libinfo-330.10-ppc-teredo-prefix.patch`. `tests/test_libinfo_ppc_teredo_prefix.py` checks the pristine Apple blob, exact one-line diff and patch, and endian arithmetic for true and false Teredo prefixes. The required `source-graph` workflow runs this source-script test. No compilation, linking, build tool, or runtime test was performed; PPC runtime behavior remains unverified.
